# COTTI 平台数据看板移植审计（v2.2.13）

## 审计结论

- 不直接移植 v2.2.8 的 `PlatformAnalyticsService`。旧实现约 720 行原始 SQL，存在统计字段过时、指标混算和未分页等问题。
- S5.1 反馈本地留存及反馈看板不移植，既有 `feedback_reports` 表本阶段不删除。
- S5.2 首批只做基于 `users`、`messages` 的总览和趋势，不改上游表结构，不增加数据库迁移。
- `messages` 是 Chat 会话事实源；`agent_operations` 是 Agent Runtime 执行事实源。两者不相加，也不使用 `GREATEST` 猜测去重。
- 统计范围为全平台，包括个人空间和所有 Workspace；只有平台管理员可以访问。

## 旧实现盘点

v2.2.8 二开实现包含：

```text
apps/server/src/services/platformAnalytics/index.ts
apps/server/src/routers/lambda/platformAnalytics.ts
src/services/platformAnalytics.ts
src/types/platformAnalytics.ts
src/features/PlatformAnalytics/index.tsx
src/routes/(main)/settings/platform-analytics/index.tsx
```

旧看板提供总览、按日趋势、用户排行、模型排行、功能使用、错误分布和反馈列表。服务端一次请求并行执行六组统计，用户和模型排行固定 `LIMIT 30/12`，没有真正的分页；前端为 830 行单体组件，页面文案硬编码中文。

## v2.2.13 结构变化和旧口径问题

| 项目               | 旧实现                                                                          | v2.2.13 事实                                                                                                       | 决策                                                                          |
| ------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| 消息 token / 成本  | 读取 `metadata.totalInputTokens`、`metadata.totalOutputTokens`、`metadata.cost` | 新写入使用独立 `messages.usage`；历史数据还可能在 `metadata.usage` 或旧平铺字段                                    | 使用统一兼容表达式，优先 `usage`，再回退 `metadata.usage`，最后回退旧平铺字段 |
| Chat 与 Agent 用量 | 按用户 / 模型合并消息和 `agent_operations`，用 `GREATEST` 避免重复              | 两张表描述不同事实，且没有稳定的一对一结果消息外键                                                                 | 分成 Chat 消息统计和 Agent 执行统计，不猜测去重                               |
| 用户排行           | `message_rollup` 已限定 `role='assistant'`，却仍返回 `userMessages`             | 该字段必然为 0；一位用户可产生多条模型行，旧 UI 又只用 `userId` 作 row key                                         | 重做类型和分页；行键至少包含 `userId/provider/model`                          |
| 模型请求数         | `max(assistantMessages, operationCount)`                                        | 既不是消息数，也不是执行数或真实 LLM 调用数                                                                        | 分别展示模型回复数、Agent 执行数和 `llmCalls`                                 |
| 活跃用户           | 任意角色消息的 `distinct user_id`                                               | 自动任务或工具消息也可能让用户 “活跃”                                                                              | 首批定义为时段内发送过 `role='user'` 消息的用户                               |
| 总消息趋势         | 对所有 message role 计数                                                        | 会把 tool/system 等内部消息混入用户交互                                                                            | 首批只统计 user 消息和 assistant 回复，合计也只由这两类组成                   |
| 工具使用           | `tools IS NOT NULL`                                                             | 空数组不代表发生工具调用                                                                                           | 后续至少排除 `NULL` 和 `[]`；不使用未经当前数据库验证的复杂 JSON 条件         |
| 联网搜索           | `search IS NOT NULL`                                                            | `GroundingSearch` 内部是可选的 query、citation 和 image 数组                                                       | 后续先用非空对象识别调用，再用生产覆盖率查询验证空对象比例                    |
| 图片 / 视频        | 统计 `generation_batches` 数量并称为 “生成量”                                   | batch 是生成请求；实际产物在 `generations`，成功状态在关联 `async_tasks`                                           | 分开展示请求数、成功产物数和失败数                                            |
| 文件协作           | 统计不重复的 `file_id`                                                          | 同一文件在多条消息使用会被压成一次                                                                                 | 后续明确展示 “使用次数” 或 “涉及文件数”，不混用                               |
| 时间边界           | `created_at >= start AND <= end`；自定义结束时间由浏览器拼接                    | 相邻区间可能在边界重复，浏览器时区也可能改变口径                                                                   | 服务端按 Asia/Shanghai 解析自然日，统一 `[startAt, endAt)`                    |
| Workspace          | 不筛选 workspace，隐含全平台                                                    | v2.2.13 多数事实表新增或强化 `workspace_id`                                                                        | 看板仍为全平台；后续如加 workspace 筛选，必须作为显式维度                     |
| 查询性能           | 一次请求运行全部重查询                                                          | `messages.created_at` 有索引；全局 `agent_operations.created_at`、`generation_batches.created_at` 不一定有适配索引 | 首批不加索引；先以生产同结构数据 `EXPLAIN` 决定                               |

## 冻结的统计边界

### 时间

- 时区固定 `Asia/Shanghai`。
- 预设范围为 1、7、30、90 个自然日。
- 自定义范围使用日期而不是浏览器本地的任意时间戳，最大 90 天。
- 数据库过滤统一使用左闭右开区间 `[startAt, endAt)`。
- 趋势补齐区间内没有数据的日期，返回 0 值。

### 权限和数据范围

- API 复用现有 COTTI 平台管理员 guard。
- 普通用户即使知道 tRPC 路径也不能读取。
- 聚合范围是全平台：个人空间和所有 Workspace 均计入。
- 首批只返回聚合数据；带用户邮箱或名称的排行留到 S5.2-4，并保持分页和管理员鉴权。

### 消息用量兼容顺序

每条 assistant 消息的用量字段按以下顺序读取：

1. `messages.usage`
2. `messages.metadata->'usage'`
3. `messages.metadata` 中旧版平铺的 `totalInputTokens`、`totalOutputTokens`、`cost`
4. 均不存在时按 0 参与求和，同时在生产验收中报告用量覆盖率

该规则与 v2.2.13 当前消息读取逻辑一致，但 SQL 实现必须对非数字 JSON 值做安全转换。

## 管理员数据工作台设计框架

### 产品任务

已确认的用户证据：

- **业务确认**：页面主要供平台管理员查看。
- **业务确认**：后续能力允许重新设计和整合，不要求保持旧版页面结构。
- **业务确认**：UI 风格需要与 LobeHub 整体一致。

基于上述事实形成的设计假设：管理员打开页面时，优先需要回答以下问题：

1. 当前有多少用户在使用，使用规模如何？
2. 消息、token 和成本在所选时段如何变化？
3. 回复错误是否增加，集中在哪些模型或使用场景？
4. 使用量主要集中在哪些用户、模型和功能？

前三个问题应在首屏完成第一次扫描；第四个问题通过同页的渐进明细回答。该假设在 S5.2-3 页面验收时通过管理员实际使用反馈验证，不把实现结构当成用户证据。

### 页面信息架构

不复刻旧版按 “总览、趋势、用户、模型、功能、反馈” 平铺的模块结构，也不让 `messages`、`agent_operations` 等数据表名称成为页面导航。建议使用一张整合的只读管理员工作台：

1. **页面头部**：平台数据、统计时段、手动刷新和数据更新时间。时间范围是整页唯一的主筛选条件。
2. **关键指标**：Chat 活跃用户、模型回复、token / 成本、回复错误率。累计用户、新增用户和活跃话题作为辅助信息，不让首屏变成卡片墙。
3. **变化趋势**：一张主趋势图，通过指标切换查看用户、消息、token、成本和错误；默认不把六条不同量纲的折线叠在一起。
4. **使用构成**：后续在同页加入用户、模型、Agent 执行和功能使用明细。列表和图表围绕 “使用集中在哪里” 组织，而不是按服务端查询文件组织。
5. **错误情况**：分别展示 Chat 回复错误和 Agent 执行错误。没有经过业务确认的阈值前，只陈述错误数量和比例，不擅自给出 “健康 / 不健康” 的红绿结论。

用户、模型或错误条目需要查看更多信息时，优先使用同页展开、侧栏或独立明细视图；只有明确的深度分析任务才离开工作台。S5.2-3 只实现前三项，后两项分别由 S5.2-4 和 S5.2-5 增量接入。

### LobeHub UI 一致性约束

- 复用现有设置页和统计页的页面骨架、间距节奏及数据展示习惯，但不复用其个人统计语义或旧 COTTI 单体组件。
- 新组件优先使用 `@lobehub/ui/base-ui`，其次使用 `@lobehub/ui`；样式优先 `createStaticStyles` 和 `cssVar.*`，不硬编码品牌色、背景色、圆角或阴影。
- 使用中性画布、克制的边框和状态色。颜色只表达状态，不作为装饰，也不作为错误与成功的唯一识别方式。
- 大数字使用共享 K / M / B / T 格式化能力，卡片显示便于扫描的短值，并提供完整精度。
- 深浅色和桌面 / 移动布局同时设计；移动端将筛选和明细自然换行或折叠，不横向压缩桌面表格。
- 用户与模型明细超过一页时使用服务端分页；筛选、排序、计数和分页都作用于完整数据集，不对当前页做客户端假筛选。

### 数据状态和交互约束

- 明确区分加载、加载失败、真实零数据和正常数据四种状态。
- 聚合请求失败时必须先显示错误与重新加载入口，禁止用默认 0 冒充真实统计结果。
- 加载状态使用稳定尺寸的 Skeleton 或项目加载组件，避免首屏跳动；不使用 antd `Spin`。
- 初版不做自动轮询；提供手动刷新和数据生成时间。后续若增加轮询，不能在管理员阅读时静默重排内容。
- 时间范围进入 URL 查询参数，使刷新、返回和分享链接能够恢复同一统计视图。
- 首批页面是只读查看面，不新增导出、告警阈值、用户管理或成本预算等尚未建模的操作。

## S5.2-2 首批服务端范围

### 总览

| 指标                   | 定义                                         | 数据源                           |
| ---------------------- | -------------------------------------------- | -------------------------------- |
| 累计用户               | 截至查询结束边界前创建的用户数               | `users.created_at < endAt`       |
| 新增用户               | 时段内创建的用户数                           | `users.created_at`               |
| Chat 活跃用户          | 时段内发送过用户消息的不重复用户数           | `messages.role='user'`           |
| 用户消息               | 时段内 user 消息数                           | `messages`                       |
| 模型回复               | 时段内 assistant 消息数                      | `messages`                       |
| 活跃话题               | 时段内 user/assistant 消息涉及的不重复 topic | `messages.topic_id`              |
| 回复错误               | 带 `error` 的 assistant 消息数               | `messages.error`                 |
| 回复错误率             | 回复错误数 /assistant 消息数                 | 派生指标                         |
| 输入 / 输出 / 总 token | assistant 消息的兼容用量求和                 | `messages.usage` 及历史 fallback |
| 记录成本               | assistant 消息的兼容 cost 求和               | `messages.usage` 及历史 fallback |
| 平均每次回复成本       | 记录成本 /assistant 消息数                   | 派生指标                         |

“模型回复” 不改称 “模型调用”：一次 Agent 执行可能有多次 LLM 调用，真正的 LLM 调用数只从 `agent_operations.llm_calls` 展示。

### 趋势

按上海自然日返回：Chat 活跃用户、用户消息、模型回复、回复错误、总 token 和记录成本。总消息数仅为用户消息与模型回复之和，不包含 tool/system 等内部消息。

### 首批明确不做

- 用户排行、用户邮箱列表。
- 模型排行和 Agent 执行指标。
- 搜索、工具、文件、图片、视频、TTS 使用分布。
- 反馈列表和反馈状态。
- Workspace 筛选。
- 缓存、物化视图、汇总表或新数据库索引。
- 前端页面；页面属于独立的 S5.2-3。
