# COTTI 平台数据看板移植审计（v2.2.13）

## 审计结论

- 不直接移植 v2.2.8 的 `PlatformAnalyticsService`。旧实现约 720 行原始 SQL，存在统计字段过时、指标混算和未分页等问题。
- S5.1 反馈本地留存及反馈看板不移植，既有 `feedback_reports` 表本阶段不删除。
- S5.2 首批只做基于 `users`、`messages` 的总览和趋势，不改上游表结构，不增加数据库迁移。
- `messages` 是 Chat 会话事实源；`agent_operations` 是 Agent Runtime 执行事实源。两者不相加，也不使用 `GREATEST` 猜测去重。
- 统计范围为全平台，包括个人空间和所有 Workspace；只有平台管理员可以访问。

## 旧实现盘点

v2.2.8 二开实现包含：

```text
apps/server/src/services/platformAnalytics/index.ts
apps/server/src/routers/lambda/platformAnalytics.ts
src/services/platformAnalytics.ts
src/types/platformAnalytics.ts
src/features/PlatformAnalytics/index.tsx
src/routes/(main)/settings/platform-analytics/index.tsx
```

旧看板提供总览、按日趋势、用户排行、模型排行、功能使用、错误分布和反馈列表。服务端一次请求并行执行六组统计，用户和模型排行固定 `LIMIT 30/12`，没有真正的分页；前端为 830 行单体组件，页面文案硬编码中文。

## v2.2.13 结构变化和旧口径问题

| 项目               | 旧实现                                                                          | v2.2.13 事实                                                                                                       | 决策                                                                          |
| ------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| 消息 token / 成本  | 读取 `metadata.totalInputTokens`、`metadata.totalOutputTokens`、`metadata.cost` | 新写入使用独立 `messages.usage`；历史数据还可能在 `metadata.usage` 或旧平铺字段                                    | 使用统一兼容表达式，优先 `usage`，再回退 `metadata.usage`，最后回退旧平铺字段 |
| Chat 与 Agent 用量 | 按用户 / 模型合并消息和 `agent_operations`，用 `GREATEST` 避免重复              | 两张表描述不同事实，且没有稳定的一对一结果消息外键                                                                 | 分成 Chat 消息统计和 Agent 执行统计，不猜测去重                               |
| 用户排行           | `message_rollup` 已限定 `role='assistant'`，却仍返回 `userMessages`             | 该字段必然为 0；一位用户可产生多条模型行，旧 UI 又只用 `userId` 作 row key                                         | 重做类型和分页；行键至少包含 `userId/provider/model`                          |
| 模型请求数         | `max(assistantMessages, operationCount)`                                        | 既不是消息数，也不是执行数或真实 LLM 调用数                                                                        | 分别展示模型回复数、Agent 执行数和 `llmCalls`                                 |
| 活跃用户           | 任意角色消息的 `distinct user_id`                                               | 自动任务或工具消息也可能让用户 “活跃”                                                                              | 首批定义为时段内发送过 `role='user'` 消息的用户                               |
| 总消息趋势         | 对所有 message role 计数                                                        | 会把 tool/system 等内部消息混入用户交互                                                                            | 首批只统计 user 消息和 assistant 回复，合计也只由这两类组成                   |
| 工具使用           | `tools IS NOT NULL`                                                             | 空数组不代表发生工具调用                                                                                           | 后续至少排除 `NULL` 和 `[]`；不使用未经当前数据库验证的复杂 JSON 条件         |
| 联网搜索           | `search IS NOT NULL`                                                            | `GroundingSearch` 内部是可选的 query、citation 和 image 数组                                                       | 后续先用非空对象识别调用，再用生产覆盖率查询验证空对象比例                    |
| 图片 / 视频        | 统计 `generation_batches` 数量并称为 “生成量”                                   | batch 是生成请求；实际产物在 `generations`，成功状态在关联 `async_tasks`                                           | 分开展示请求数、成功产物数和失败数                                            |
| 文件协作           | 统计不重复的 `file_id`                                                          | 同一文件在多条消息使用会被压成一次                                                                                 | 后续明确展示 “使用次数” 或 “涉及文件数”，不混用                               |
| 时间边界           | `created_at >= start AND <= end`；自定义结束时间由浏览器拼接                    | 相邻区间可能在边界重复，浏览器时区也可能改变口径                                                                   | 服务端按 Asia/Shanghai 解析自然日，统一 `[startAt, endAt)`                    |
| Workspace          | 不筛选 workspace，隐含全平台                                                    | v2.2.13 多数事实表新增或强化 `workspace_id`                                                                        | 看板仍为全平台；后续如加 workspace 筛选，必须作为显式维度                     |
| 查询性能           | 一次请求运行全部重查询                                                          | `messages.created_at` 有索引；全局 `agent_operations.created_at`、`generation_batches.created_at` 不一定有适配索引 | 首批不加索引；先以生产同结构数据 `EXPLAIN` 决定                               |

## 冻结的统计边界

### 时间

- 时区固定 `Asia/Shanghai`。
- 预设范围为 1、7、30、90 个自然日。
- 自定义范围使用日期而不是浏览器本地的任意时间戳，最大 90 天。
- 数据库过滤统一使用左闭右开区间 `[startAt, endAt)`。
- 趋势补齐区间内没有数据的日期，返回 0 值。

### 权限和数据范围

- API 复用现有 COTTI 平台管理员 guard。
- 普通用户即使知道 tRPC 路径也不能读取。
- 聚合范围是全平台：个人空间和所有 Workspace 均计入。
- 首批只返回聚合数据；带用户邮箱或名称的排行留到 S5.2-4，并保持分页和管理员鉴权。

### 消息用量兼容顺序

每条 assistant 消息的用量字段按以下顺序读取：

1. `messages.usage`
2. `messages.metadata->'usage'`
3. `messages.metadata` 中旧版平铺的 `totalInputTokens`、`totalOutputTokens`、`cost`
4. 均不存在时按 0 参与求和，同时在生产验收中报告用量覆盖率

该规则与 v2.2.13 当前消息读取逻辑一致，但 SQL 实现必须对非数字 JSON 值做安全转换。

## 管理员数据工作台设计框架

### 产品任务

已确认的用户证据：

- **业务确认**：页面主要供平台管理员查看。
- **业务确认**：后续能力允许重新设计和整合，不要求保持旧版页面结构。
- **业务确认**：UI 风格需要与 LobeHub 整体一致。

基于上述事实形成的设计假设：管理员打开页面时，优先需要回答以下问题：

1. 当前有多少用户在使用，使用规模如何？
2. 消息、token 和成本在所选时段如何变化？
3. 回复错误是否增加，集中在哪些模型或使用场景？
4. 使用量主要集中在哪些用户、模型和功能？

前三个问题应在首屏完成第一次扫描；第四个问题通过同页的渐进明细回答。该假设在 S5.2-3 页面验收时通过管理员实际使用反馈验证，不把实现结构当成用户证据。

### 页面信息架构

不复刻旧版按 “总览、趋势、用户、模型、功能、反馈” 平铺的模块结构，也不让 `messages`、`agent_operations` 等数据表名称成为页面导航。建议使用一张整合的只读管理员工作台：

1. **页面头部**：平台数据、统计时段、手动刷新和数据更新时间。时间范围是整页唯一的主筛选条件。
2. **关键指标**：Chat 活跃用户、模型回复、token / 成本、回复错误率。累计用户、新增用户和活跃话题作为辅助信息，不让首屏变成卡片墙。
3. **变化趋势**：一张主趋势图，通过指标切换查看用户、消息、token、成本和错误；默认不把六条不同量纲的折线叠在一起。
4. **使用构成**：后续在同页加入用户、模型、Agent 执行和功能使用明细。列表和图表围绕 “使用集中在哪里” 组织，而不是按服务端查询文件组织。
5. **错误情况**：分别展示 Chat 回复错误和 Agent 执行错误。没有经过业务确认的阈值前，只陈述错误数量和比例，不擅自给出 “健康 / 不健康” 的红绿结论。

用户、模型或错误条目需要查看更多信息时，优先使用同页展开、侧栏或独立明细视图；只有明确的深度分析任务才离开工作台。S5.2-3 只实现前三项，后两项分别由 S5.2-4 和 S5.2-5 增量接入。

### LobeHub UI 一致性约束

- 复用现有设置页和统计页的页面骨架、间距节奏及数据展示习惯，但不复用其个人统计语义或旧 COTTI 单体组件。
- 新组件优先使用 `@lobehub/ui/base-ui`，其次使用 `@lobehub/ui`；样式优先 `createStaticStyles` 和 `cssVar.*`，不硬编码品牌色、背景色、圆角或阴影。
- 使用中性画布、克制的边框和状态色。颜色只表达状态，不作为装饰，也不作为错误与成功的唯一识别方式。
- 大数字使用共享 K / M / B / T 格式化能力，卡片显示便于扫描的短值，并提供完整精度。
- 深浅色和桌面 / 移动布局同时设计；移动端将筛选和明细自然换行或折叠，不横向压缩桌面表格。
- 用户与模型明细超过一页时使用服务端分页；筛选、排序、计数和分页都作用于完整数据集，不对当前页做客户端假筛选。

### 数据状态和交互约束

- 明确区分加载、加载失败、真实零数据和正常数据四种状态。
- 聚合请求失败时必须先显示错误与重新加载入口，禁止用默认 0 冒充真实统计结果。
- 加载状态使用稳定尺寸的 Skeleton 或项目加载组件，避免首屏跳动；不使用 antd `Spin`。
- 初版不做自动轮询；提供手动刷新和数据生成时间。后续若增加轮询，不能在管理员阅读时静默重排内容。
- 时间范围进入 URL 查询参数，使刷新、返回和分享链接能够恢复同一统计视图。
- 首批页面是只读查看面，不新增导出、告警阈值、用户管理或成本预算等尚未建模的操作。

## S5.2-2 首批服务端范围

### 总览

| 指标                   | 定义                                         | 数据源                           |
| ---------------------- | -------------------------------------------- | -------------------------------- |
| 累计用户               | 截至查询结束边界前创建的用户数               | `users.created_at < endAt`       |
| 新增用户               | 时段内创建的用户数                           | `users.created_at`               |
| Chat 活跃用户          | 时段内发送过用户消息的不重复用户数           | `messages.role='user'`           |
| 用户消息               | 时段内 user 消息数                           | `messages`                       |
| 模型回复               | 时段内 assistant 消息数                      | `messages`                       |
| 活跃话题               | 时段内 user/assistant 消息涉及的不重复 topic | `messages.topic_id`              |
| 回复错误               | 带 `error` 的 assistant 消息数               | `messages.error`                 |
| 回复错误率             | 回复错误数 /assistant 消息数                 | 派生指标                         |
| 输入 / 输出 / 总 token | assistant 消息的兼容用量求和                 | `messages.usage` 及历史 fallback |
| 记录成本               | assistant 消息的兼容 cost 求和               | `messages.usage` 及历史 fallback |
| 平均每次回复成本       | 记录成本 /assistant 消息数                   | 派生指标                         |

“模型回复” 不改称 “模型调用”：一次 Agent 执行可能有多次 LLM 调用，真正的 LLM 调用数只从 `agent_operations.llm_calls` 展示。

### 趋势

按上海自然日返回：Chat 活跃用户、用户消息、模型回复、回复错误、总 token 和记录成本。总消息数仅为用户消息与模型回复之和，不包含 tool/system 等内部消息。

### 首批明确不做

- 用户排行、用户邮箱列表。
- 模型排行和 Agent 执行指标。
- 搜索、工具、文件、图片、视频、TTS 使用分布。
- 反馈列表和反馈状态。
- Workspace 筛选。
- 缓存、物化视图、汇总表或新数据库索引。
- 前端页面；页面属于独立的 S5.2-3。

S5.2-4E Agent 生产诊断结果（2026-08-03）：

- 已在生产以只读事务运行 7/30/90 天 `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)`；事务设置 3 秒锁等待、30 秒语句超时并最终 `ROLLBACK`，没有修改数据或 schema。
- 生产 `agent_operations` 估算 917 行，表与索引合计约 2 MB；90 天包含 902 个根 operation、15 个子 operation 和 38 个根 Agent 分组。所有 Agent、父 operation 和 trigger 均可解析，没有嵌套在子 operation 下的第二层子执行。
- 最终候选聚合只读取 `done/error/interrupted` 的根 operation。7/30/90 天实际执行时间分别约 3.82/3.70/3.91 ms，均为内存 quicksort、共享缓存命中，无磁盘排序或临时文件。
- 当前计划选择顺序扫描是合理结果；表很小且 90 天覆盖几乎全部行，现在新增全局 `created_at` 或根 operation 部分索引只会增加写入和维护成本。因此 4F 不新增迁移或索引。
- 当 operation 规模达到当前约 10 倍，或 Agent 明细 API 的生产 p95 超过 100 ms 时重新执行本诊断；只有届时范围扫描成为主要成本，才另行评估 `created_at` 的在线部分索引，不在功能提交中顺带创建。
- 902 个根 operation 中，LLM/tool/token 各有 12 条未记录，成本有 236 条未记录，执行时长全部有记录。因此页面只能展示 “记录成本”，API 同时返回 token / 成本有记录的执行数，不能把缺失值解释为真实零。
- 状态分布为 881 次完成、11 次错误和 10 次中断；trigger 分布为 884 次 task、18 次 chat。trigger 是调用来源而不是管理员的查找对象，首版不提升为顶层标签或排行维度。

4F 冻结的管理员查找对象仍是根 Agent。只聚合已结束的根 operation，并返回 Agent 身份、执行数、活跃用户、错误数、中断数、LLM/tool calls、输入 / 输出 / 总 token、记录成本、token / 成本覆盖执行数、平均执行时长和最后执行时间。子 operation 不单独成行，也不二次求和；原始 operation、trace、provider/model 和 trigger 明细不进入首版页面。

- 已在同一 “使用明细” 区域加入 Agent 标签；用户、模型、Agent 三个列表分别保存 URL 搜索、排序、页码和每页数量，切换后互不覆盖。
- Token 与记录成本均提供覆盖执行数提示，缺失计量不会被描述为真实零；执行结果同时保留错误率和中断率，执行耗时明确为 operation 平均执行时长。
- 没有新增 schema、迁移、索引、全局 store 或新页面路由，也没有展示原始 operation、trace、provider/model 或 trigger。

#### 用户任务与证据

- **业务确认**：该页面主要供平台管理员查看，允许重新设计整合，不要求复刻旧版页面。
- **业务确认**：工作台保持只读，本轮没有提出用户处置、导出或预算控制任务。
- **系统证据**：Chat 消息、Agent operation 是两类不同事实；父 operation 的资源标量会汇总直接子 Agent。
- **设计假设**：管理员进入使用明细时，需要先回答 “使用主要集中在哪些同事、哪些 Chat 模型和哪些 Agent”，再决定是否深入排查异常。该假设在 S5.2-4D 用管理员实际查找任务验证，不把旧版排行结构当成用户证据。

#### 事实源审计结论（2026-08-03）

- Chat 用户和模型明细可以直接从 `messages` 统计；其 `created_at` 已有全局索引，并可复用 S5.2-2 已验证的历史 usage fallback。
- 旧版先按 `user/provider/model` 生成多行，再把 Chat 回复与 Agent operation 用 `GREATEST` 合并成 “请求数”、token、成本和错误。该口径无法说明到底统计了回复、执行还是调用，不移植。
- Chat 用户的查找对象应是用户，而不是 “用户 × 模型” 组合；用户行按 `user_id` 聚合，模型构成留在模型视图，不让一位用户重复出现多行。
- Chat 模型的事实是 assistant 回复；它不能被称为 “LLM 调用”。真正的 `llm_calls` 只存在于 Agent operation。
- `agent_operations` 的根 operation 完成时，标量 token、成本、LLM/tool calls 已经包含直接子 Agent 的汇总；如果再把父子行一起求和会重复计费。
- Agent 使用应先按根 operation（`parent_operation_id IS NULL`）和根 Agent 聚合。子 Agent 行可用于解释 “派生了多少次子执行”，但不能再叠加进根 operation 的资源总量。
- 根 operation 的 provider/model 只表示根 Agent，不能代表子 Agent 实际使用的模型；因此本阶段不做 “Agent 模型排行”，只做 Chat 模型排行和 Agent 使用排行。
- `agent_operations` 当前只有 `(user_id, created_at)` 联合索引，没有全平台 `created_at` 索引。Agent 全平台范围查询必须先做生产只读 `EXPLAIN`，不能与 Chat 明细一起无条件上线。

#### 冻结的 Chat 用户明细

每行是一位当前用户，使用 `user_id` 作为稳定行键。只返回管理员查找同事所需的 `fullName/username/email/avatar`，不返回手机号、认证信息、偏好或消息内容。

| 字段                     | 定义                                                                |
| ------------------------ | ------------------------------------------------------------------- |
| 用户消息 /assistant 回复 | 时段内 `role='user'/'assistant'` 数量                               |
| 活跃天数                 | 时段内发送过 user 消息的上海自然日数量                              |
| 最后活跃时间             | 时段内最后一条 user 消息时间；自动回复不伪装成用户主动活跃          |
| 活跃话题                 | 时段内 user/assistant 消息涉及的不重复 `topic_id`                   |
| token / 记录成本         | 该用户 assistant 消息的兼容 usage 求和                              |
| 回复错误 / 错误率        | 带 error 的 assistant 消息数量，以及它占该用户 assistant 回复的比例 |

- 支持服务端姓名 / 用户名 / 邮箱搜索、服务端排序和服务端分页。
- 默认按总 token 降序；可按回复数、记录成本、错误数、最后活跃时间切换。
- 默认每页 20 条，最大 50 条；搜索、排序、总数和分页都作用于完整时间范围，不在当前页做客户端处理。
- 被删除用户的 Chat 消息会随用户级联删除，因此 Chat 用户明细不制造 “已删除用户” 占位行。

#### 冻结的 Chat 模型明细

每行以 `provider + model` 作为组合行键，只聚合 assistant 消息：活跃用户、回复数、错误数 / 错误率、输入 / 输出 / 总 token 和记录成本。

- provider/model 缺失时保留一个未归属分组并返回空值，不写入或返回人为的 `unknown` 哨兵字符串；这样既不丢总量，也不把缺失归属伪装成模型。
- 支持 provider/model 服务端搜索、服务端排序和服务端分页，默认按总 token 降序。
- 不返回 Agent `llmCalls`、tool calls 或 latency；这些不是 Chat 消息事实。

#### Agent 使用明细的后置条件

Agent 明细的查找对象是根 Agent，而不是 operation 日志或 provider/model。根 operation 数量表示 Agent 执行数，根行的汇总标量表示整棵直接子 Agent 执行树的 LLM/tool calls、token 和成本。

开始实现前必须完成：

1. 在生产同结构数据上分别对 7/30/90 天根 operation 聚合运行 `EXPLAIN (ANALYZE, BUFFERS)`。
2. 确认根 operation 数量、子 operation 数量，以及 `parent_operation_id`、`agent_id`、`trigger` 的空值覆盖率。
3. 根据证据决定是否新增全局 `created_at` 或适合根 operation 范围查询的部分索引；如需索引，独立走在线迁移。
4. UI 将耗时命名为 “执行时长”，不称 “模型延迟”；`processing_time_ms` 覆盖整个 operation 生命周期，并非单次 LLM latency。

S5.2-5A 生产事实源诊断结果（2026-08-03）：

#### 冻结的能力采用视图

管理员的查找对象是用户可理解的 “平台能力”，不是数据表或内部工具标识。首版固定为：

1. **联网检索**：模型内置有效 search 消息数、网页搜索工具结果数，以及两类来源合并去重后的活跃用户数。两种事件可以作为同一能力的采用证据，但保留来源拆分。
2. **工具使用**：持久化工具结果数、活跃用户、错误结果和拒绝 / 中止结果。网页搜索是工具使用的一个子集，所以各能力不是互斥分桶，禁止将卡片求和成 “总请求数”。
3. **文件输入**：文件 — 用户消息关系数、涉及消息数、不重复文件数和活跃用户数。
4. **图片生成 / 视频生成**：generation batch 请求数、generation 结果行、成功文件、错误结果、无结果请求和活跃用户。视频在当前生产真实返回零值，不制造使用量。

这些能力的数据结构不同，不设计一个通用的 `count` 字段或强行排行。API 返回有名称的具体指标，UI 使用同一视觉容器展示各自的主指标和验证信息。

#### 冻结的错误视图

- **Chat 回复错误**：按 provider、model 和安全 category 聚合错误回复数与受影响用户数；不返回 `message/body`。
- **Agent 执行错误**：只统计终态错误的根 operation，按根 Agent 和安全 category 聚合错误执行数与受影响用户数；不展开子 operation，也不返回 trace 或错误原文。
- **工具结果错误**：留在 “工具使用” 能力中作为结果质量，不升级成第三类终态错误，避免一条工具失败和其所在 Agent 根执行失败被重复陈述。
- 未经业务确认不设置 “健康 / 不健康” 阈值；页面只描述数量、比例和集中位置。

4. **S5.2-5D 错误分布 API**：新增 Chat / Agent 两类安全分类聚合、服务端分页和管理员 router；不返回错误原文。
