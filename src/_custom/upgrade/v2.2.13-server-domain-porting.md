# COTTI 服务端能力按业务域移植清单（v2.2.13）

## 目标与约束

- 基线：官方 `v2.2.13`。
- 来源：生产分支 `release/db-migration-home-notification-current` 相对 `v2.2.8` 的二开能力。
- 目标：保留仍有业务价值的 COTTI 能力，不把旧版本实现方式原样搬进新架构。
- 约束：优先新增 COTTI 文件；只有路由注册、鉴权执行和数据采集等无法旁路的位置才修改上游文件。
- 每个业务域单独提交、单独测试、可单独回退。禁止一次性 cherry-pick 跨域旧提交。

## 统一落位规则

新增服务端代码统一落在以下位置：

```text
apps/server/src/routers/lambda/cotti/   # COTTI tRPC 路由
apps/server/src/services/cotti/         # COTTI 服务与策略
src/_custom/                            # COTTI 前端、注册表、升级文档
src/types/cotti/                        # 需要前后端共享的 COTTI API 类型
packages/database/src/models/cotti*     # COTTI 数据模型（已经存在）
packages/database/src/schemas/cotti*    # COTTI 表结构（已经存在）
```

根路由只注册一个 `cotti` 子路由：

```text
lambdaClient.cotti.admin
lambdaClient.cotti.agentAccess
lambdaClient.cotti.homeNotification
lambdaClient.cotti.modelDisplay
lambdaClient.cotti.platformAnalytics
lambdaClient.cotti.platformAudit
```

这样后续增加 COTTI API 时，不再反复修改上游根路由。

## 实施阶段与小步骤

### S1：COTTI 服务端骨架与平台管理员鉴权

1. 新建 `routers/lambda/cotti/index.ts`，只暴露 COTTI 子路由。
2. 在根 `lambdaRouter` 注册一次 `cotti: cottiRouter`。
3. 新建 `services/cotti/adminAccess.ts`。
4. 管理员判定兼容生产环境变量 `COTTI_PLATFORM_ANALYTICS_ADMIN_EMAILS`。
5. 同时识别 v2.2.13 全局 RBAC 角色 `super_admin`，并兼容生产既有的 Better Auth `users.role=admin`；不自动创建或修改任何角色数据。
6. 新增 `cotti.admin.getAccess`，供平台管理入口做服务端权限确认。
7. 单测覆盖：未登录、普通用户、邮件白名单、规范化邮件、`super_admin`、通配符配置。

验收：普通用户得到 `FORBIDDEN`；两类管理员可访问；不改变现有普通 LobeHub API。

### S2：低耦合平台配置

#### S2.1 首页通知

1. 移植公开读取和管理员更新两个 API 到 `cotti.homeNotification`。
2. 复用现有 `CottiHomeNotificationModel`，不改 schema。
3. 输入 schema 放在 COTTI 路由内，共享返回类型放入 COTTI 类型目录。
4. 增加路由权限测试、空配置默认值测试和更新测试。

验收：未登录用户只能读取；管理员可更新；普通登录用户不能更新。

#### S2.2 平台模型展示配置

1. 移植配置读取、模型选项读取、管理员更新 API。
2. 复用 `CottiModelDisplayModel`，保留 Chat 与 Agent 两套列表。
3. 将 “平台可见模型” 接入 v2.2.13 的 `aiProviderAccess` 策略层，不向 `AiInfraRepos` 重新塞旧版构造参数。
4. 明确策略合并顺序：上游 / 用户禁用优先，COTTI 平台配置只能进一步收窄，不能重新放开被上游禁止的模型。
5. 保留 v2.2.13 用户模型显示名能力；COTTI 配置只覆盖平台指定模型的展示名。
6. 增加 Chat/Agent 场景过滤、分页后过滤、运行时状态过滤和显示名测试。

验收：平台关闭的模型不出现在对应场景；用户和上游的禁用规则不被绕过；现有模型运行时不受无关配置影响。

客户端场景过滤实现记录（2026-08-03）：

1. 保持 v2.2.13 全站共享的 AI Provider Runtime State，不按页面重复请求或覆盖全局模型状态。
2. 新增 COTTI 模型展示配置客户端服务，模型选择器通过 SWR 复用一次 Chat/Agent 双列表配置。
3. `ModelSwitchPanel` 增加可选的 `modelDisplayScope`；只有 Chat 输入区传入当前有效的 `chat` / `agent` 模式，图片、视频、Copilot 等官方复用入口保持原行为。
4. 配置加载完成后按目标场景过滤、排序并覆盖平台展示名；加载期间保留服务端已经裁剪过的 Chat/Agent 并集，避免选择器闪空。
5. 配置增加独立的 `defaults.chat` 与 `defaults.agent`，缺省模型不依赖列表第一项；历史配置读取时补齐 COTTI - 快速与 COTTI - 专业缺省值，不新增数据库列或迁移。
6. 模式切换时，当前模型仍属于目标场景则保持不变；否则先切换到目标场景缺省模型，再切换模式。Topic 固定模型、个人 Agent 与 Workspace 成员覆盖继续走各自现有写入路径。
7. 缺省模型必须在对应场景启用且对当前用户实际可用；平台配置无效或模型已被上游用户策略隐藏时，不切换模式，也不绕过上游权限。

### S3：飞书蓝标第二 SSO

1. 增加 `AUTH_FEISHU_BLUE_APP_ID` 和 `AUTH_FEISHU_BLUE_APP_SECRET` 环境声明与校验。
2. 将现有 Feishu provider 提取为同文件工厂，保持默认 `feishu` 行为不变。
3. 注册 `feishu-blue` provider，使用独立 provider ID 和回调地址。
4. 无真实密钥单测 provider 注册、缺失变量报错、两个 provider ID 与 fallback email 域隔离。
5. 在 dev 使用测试应用完成一次登录回调验收。

验收：原飞书登录不回归；蓝标账号生成独立 account/provider 绑定；不会串号。

### S3.1：个人飞书资料连接器

个人飞书 OAuth/MCP 连接器是独立于登录 SSO 的二开域。中文界面的用户可见名称、输入框 action tag 和服务端运行时标题统一为 “飞书资料”；稳定 identifier `feishu-documents` 与飞书 MCP 工具名不翻译，避免破坏授权和工具路由。完整触点及升级回放规则见 [`v2.2.13-feishu-documents-connector.md`](./v2.2.13-feishu-documents-connector.md)。

2026-08-05 在原个人只读资料能力上新增飞书官方 `create-doc`，用于把聊天记录新建为用户自己的飞书文档。仍不开放 `update-doc`、评论、消息写入或删除类工具；新增 scopes、重新授权要求和双层工具白名单见上述专项文档。

### S3.2：Composio 连接器对话框可用性

2026-08-05 在 chatdev 完成 Gmail OAuth 后，设置页显示连接成功且 20 个 Gmail 工具已入库，但输入框 `@` 选择器只显示飞书资料。该问题由三个独立缺口叠加：

1. `useInstalledSkillsAndTools` 只读取 `composioServers`，自身未调用 `useFetchUserComposioConnections`，错误地依赖工具弹框等其他页面先挂载。
2. Composio SWR 成功后只追加新 identifier，不会用服务端 `ACTIVE` 行替换内存中的同名 `PENDING_AUTH` 行，也不会清理远端已删除的个人连接。
3. `connector.syncPluginTools` 更新展示信息时整体替换 `user_connectors.metadata`，清除了 `metadata.composio` 中的 Connected Account、Auth Config、授权用户和状态；旧 `user_installed_plugins` 仍然完整，因此界面看似连接成功但新版 Connector Runtime 无法识别。

二开保留规则：

1. `src/features/ChatInput/InputEditor/ActionTag/useInstalledSkillsAndTools.ts` 必须让 `@` 入口独立加载当前用户的 Composio 连接，不依赖其他页面的副作用。
2. `src/store/tool/slices/composioStore/action.ts` 以服务端返回值作为个人连接的 canonical snapshot，替换同名本地状态并清理远端已删除项；服务端接口不返回的 Agent-scoped 连接必须保留。
3. `apps/server/src/routers/lambda/connector.ts` 的通用 manifest 同步只覆盖 `avatar`、`description` 等展示字段，必须合并既有 metadata，禁止删除 `composio`、挂载锁等其他业务字段。
4. 不新增数据库表或迁移。历史受影响行从同用户、同 identifier 的 `user_installed_plugins.custom_params.composio` 做带条件回填；只修复缺少 `metadata.composio` 且 legacy 投影仍为 `ACTIVE` 的行。
5. 回归检查必须覆盖：`@` 入口触发加载并出现 Gmail、PENDING→ACTIVE 替换、远端删除清理、Agent-scoped 行保留、插件工具同步保留 Composio metadata。

### S4：Agent 智能入口渐进开放

本域控制的是 Chat 页面中 Agent 智能模式入口的展示和交互门槛，不是服务端安全权限。未开通用户仍可正常使用 Chat、搜索、知识库、记忆及底层运行时能力；直接 API 调用不作为绕过处理。

#### S4.1 入口显示范围服务端配置

1. 移植 `open/off/allowlist`、身份规范化和环境变量 fallback 策略。
2. 复用 `CottiAgentAccessModel`，数据库设置存在时优先于环境变量。
3. 新增普通用户状态查询及管理员配置、用户搜索 API 到 `cotti.agentAccess`。
4. API 和管理文案统一使用 “Agent 智能模式入口显示范围”，不描述为运行时权限。
5. 对同一请求中的重复状态判定做请求级复用。

#### S4.2 客户端渐进展示

1. 通过现有 Business Agent Mode Hook 读取当前用户的入口状态。
2. 未开通时保留 Agent 智能选项但置灰，显示锁定状态。
3. 悬停、键盘聚焦或移动端点击时提示 “Agent 智能模式需完成基础培训后开通，请联系平台管理员申请”。
4. 区分管理员未开通、模型不支持和状态加载中的禁用原因。
5. 不修改 Agent Runtime、Agent 创建更新接口、Workspace 偏好、异构 Agent、Group Agent 或定时任务执行链。

验收：开通用户可以选择 Agent 智能模式；未开通用户看到明确的置灰入口与申请提示；所有用户的 Chat 和服务端运行时能力保持不变。

实现记录（2026-08-03）：

1. 新增 `cottiAgentAccessService.getStatus`，客户端只读取 S4.1 的当前用户入口状态。
2. 通过现有 `useBusinessAgentMode` 扩展点接入 SWR 状态，显式暴露加载、已解析、错误、刷新和可见性；后台刷新失败时保留已解析状态。
3. `useEffectiveAgentMode` 仅将未开通或尚未解析的界面有效模式降为 Chat，不回写 Agent 配置或 Workspace 用户偏好。
4. 同步接入 ControlBar 与兼容 ActionBar 两个现存模式入口：未开通时保留 Agent 选项、置灰并显示锁图标；悬停和键盘聚焦显示申请提示，移动端打开模式菜单即可看到同一提示。
5. 状态加载、首次加载失败、管理员未开通和模型不支持使用不同提示；首次加载失败时点击 Agent 选项可重新检查状态。
6. 定向验证覆盖开通、未开通、加载中、后台刷新失败和模型能力回退；未增加 Agent Runtime 或服务端写链路限制。

#### S4.3 首页 Agent 智能启动入口

实现记录（2026-08-20）：

1. 首页启动模式固定按 “对话 Chat → 智能 Agent → 任务 Task” 排列；中文表达用户意图，英文对应系统模式。
2. “智能 Agent” 与 “对话 Chat” 都在当前选中 Agent 下创建独立 Topic，不新增路由、数据库字段或 Agent Runtime 分支；发送前复用现有 `useToggleAgentMode` 完成模式与模型池切换，下级会话页继续读取同一份 Agent 配置或 Workspace 用户偏好。
3. 当前 Chat 模型不属于 Agent 模型池时继续使用平台配置的 Agent 缺省模型，不按候选列表第一项猜测；首页模型选择器随启动模式切换 `chat` / `agent` 展示范围。
4. 首页内部 `inputActiveMode='agent'` 仍表示 “创建 Agent” 的 Agent Builder。只有 “对话 Chat” 消费 Starter Mode；“智能 Agent” 始终进入所选 Agent 的会话，禁止两个同名概念串线。
5. “智能 Agent” 复用普通会话的上传、已选上下文和最近会话区域；Agent 专用表格可以发送，普通 Chat 继续拦截并保留草稿，Task 继续不接收附件与上下文。
6. 首页 Agent 入口复用 S4.1 准入状态；未开通、尚未解析或无创建权限时置灰并回退到 Chat，不扩大为服务端运行时权限。
7. 回归检查覆盖模式顺序与中英文标签、准入回退、Agent 模型作用域、发送前模式切换失败保留草稿、Agent 专用附件，以及 Agent 智能不会误调用 Agent Builder。

## 暂缓域的重新启用条件

### 定时任务隔离

必须先确认以下业务问题：

- 定时任务是否允许读取当前 Agent 的文档和知识库？
- 是否允许读取话题历史？
- 是否允许执行 `lh agent/doc/file/kb/message/topic`？
- “隔离” 是防止数据越权，还是仅避免污染当前会话？

只有答案明确后，先为 v2.2.13 写失败测试，再在新 Runtime 的单一策略边界实现。旧 `taskIsolationPolicy.ts` 不直接移植。

### Payload 裁剪

2026-08-04 已通过 chatdev 真实任务确认 Excel 附件路由缺陷：约 828KB 的 XLSX 被解析为约 133 万字符并全文注入首次 Vertex AI 请求，在 Agent 获得 `executeCode` 调用机会前超过 1,048,576 Token 输入上限。处理边界如下：

1. 普通 Chat 保留官方直接读取小 Excel 的能力；超过 128KB、一次上传多份 Excel、或单份 XLSX 包含多个有效 Sheet 时，文件仍上传并显示，但禁止 Chat 发送，提示用户切换 Agent 模式后复用同一文件。
2. Agent 与异构 Agent 上传文件后不触发普通 Chat 的正文解析流程，由其运行环境和工具读取原文件。
3. 服务端附件解析与 Context Engine 在 Agent 模式下对 Excel/CSV 仅注入文件 ID、名称、类型、大小和 URL，不注入解析正文；普通 Chat 默认保持官方解析策略。
4. 云沙箱继续复用官方附件同步和 `executeCode` 能力，不新增文件存储或解析服务。
5. “随消息发送” 只建立消息附件关系；“添加为知识” 才建立 Agent 长期关系并触发 chunk/embedding。
6. 完整触点、数据落点、升级回放顺序和验收清单见 [`v2.2.13-message-attachments-and-knowledge.md`](./v2.2.13-message-attachments-and-knowledge.md)。
