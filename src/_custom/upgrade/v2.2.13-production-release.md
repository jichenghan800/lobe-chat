# v2.2.13 COTTI 生产发版与历史数据保护

## 背景

生产已知基线为 COTTI `0118`，目标代码包含结构对账迁移 `0119` 和人员管理迁移
`0120`。`0119` 之前还需要完成历史设备可见性回填和在线热点索引；迁移之后需要补齐
Topic Comment RBAC。因此本次不能复用 v2.2.8 的 “应用启动时直接迁移并换镜像” 脚本。

## 发布策略

采用 expand-first：旧应用在线时完成镜像拉取、完整备份验证、历史回填、`0119/0120`
和 RBAC 后置同步，所有数据库门禁通过后才仅重建 `app`。PostgreSQL、QStash、SearXNG
不重建、不换镜像。

## 二开发布工具

发布实现集中在 `src/_custom/deploy/`：

- `build-production-image.sh`：从干净提交创建临时构建上下文，只复制公开编译配置；
- `create-production-app-update-package.sh`：按不可变 digest 生成无密钥发布包；
- `prod-01-check-runtime.sh`：生产只读环境、四容器、配置和迁移冲突检查；
- `prod-02-backup-and-migrate.sh`：完整备份恢复验证、历史指纹、前置回填、迁移和 RBAC；
- `prod-03-switch-app.sh`：保留服务器密钥，只同步非密配置并切换 app；
- `prod-04-verify-app-update.sh`：镜像、数据库、历史数据、OIDC、QStash 和启动验收；
- `prod-05-rollback-app.sh`：只回退应用和运行配置，不自动覆盖数据库。

应用候选提交与发布工具提交分别记录。生产镜像的 OCI revision 必须等于 chatdev 已验收的
应用提交；之后新增的发布脚本和文档提交不能悄悄改变应用候选版本。

## 历史数据不丢失边界

1. PostgreSQL dump 必须能完整恢复到临时数据库，不能只校验归档目录。
2. 历史表行数以恢复出的备份快照为基线，迁移后和最终验收时均禁止减少。
3. dump、SHA-256、归档清单、行数指纹、`.env`、Compose 和 SearXNG 配置均留存在
   生产 `backups/`。
4. 普通回滚保留 `0120` schema，避免恢复旧 dump 覆盖发版后的用户写入。
5. 数据库恢复不进入自动脚本；如果必须恢复，应先备份故障现场，并由业务明确接受备份
   时刻之后的写入损失。

## 升级回放

后续版本先检查官方是否已经提供独立 migration job、在线迁移和可验证备份流程。如果没有，
继续保留 “前置数据脚本 → 一次性 migration container → 后置数据脚本 → app switch” 的顺序。
不得退回到 “重启 app 时顺带执行所有迁移” 的旧流程。
