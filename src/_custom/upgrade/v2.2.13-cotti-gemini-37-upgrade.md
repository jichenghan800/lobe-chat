# COTTI 专业模型升级到 Gemini 3.7 Flash

## 二开范围

- `COTTI-快速` 保持 `vertexai/gemini-3.5-flash-lite`。
- `COTTI-专业` 默认从 `vertexai/gemini-3.6-flash` 升级到
  `vertexai/gemini-3.7-flash`；两个版本都保留为已部署候选模型。
- 平台管理员可以在 “平台管理 → 模型” 中切换 `COTTI-专业` 的底层版本。用户侧始终只显示
  一个 `COTTI-专业` 渠道，不增加灰度路由或重复模型入口。
- COTTI 模型展示、历史数据升级和后台切换继续作为独立二开层；Gemini 3.7 的 Google / Vertex
  AI 模型卡、知识截止时间和 Thinking 默认参数采用 LobeHub 官方实现。

## 模型依据

Google Cloud Model Garden：

`https://console.cloud.google.com/agent-platform/publishers/google/model-garden/gemini-3.7-flash`

- Resource ID：`gemini-3.7-flash`
- 发布时间：2026-08-13
- 阶段：GA
- 输入：文本、图片、视频、音频和 PDF
- 输出：文本
- 输入上限：1M token
- 输出上限：64K token
- 官方说明价格与 Gemini 3.6 Flash 相同

chatdev 使用现有 Vertex AI 服务账号完成了文本生成、函数调用、Google Search grounding
和三模型性能基准。3.7 在本轮定向任务中为 15/15，完整回复中位耗时比 3.6 低 40.9%。

### Thinking level 兼容

Google 通用 Thinking 文档截至 2026-08-14 尚未把 3.7 加入支持矩阵。使用 chatdev
同一 Vertex AI 项目、`global` 区域和 `@google/genai` SDK 实测：

- 不传 `thinkingLevel`：成功；
- `low`、`medium`、`high`：成功；
- `minimal`：固定返回 `400 INVALID_ARGUMENT`，错误为
  `Thinking level is unsupported: THINKING_LEVEL_MINIMAL`。

因此 3.7 按 LobeHub 官方实现使用仅包含 `low / medium / high` 的 `thinkingLevel3` 控件，
默认值为 `medium`。不在共享 Google Provider 中增加模型专属特判，避免二开运行时与后续
官方升级冲突。

升级脚本也会把已经迁移到 3.7 的 Agent 中旧版 `chatConfig.thinkingLevel` 一次性改为
`chatConfig.thinkingLevel3`；其中 `minimal` 映射为 `low`，其余三档保持原值。脚本完成后
旧字段计数必须为 0，并继续保持幂等。后台在 3.6 / 3.7 之间切换时也执行同样的字段转换，
因此历史 `minimal` 不会进入 3.7 的运行时请求。

## 官方实现基线

- 上游提交：`14ec086c22113041b92e532703cb1e7027944f19`
- 上游能力：Google 与 Vertex AI 模型卡、`knowledgeCutoff: 2026-03`、
  `thinkingLevel3` 和 `medium` 默认值。
- 未整体 cherry-pick 上游提交，因为该提交同时包含 GLM-5.3、DeepSeek V4 GA 和推理参数
  UI 重构；本项目仅选择性移植 Gemini 3.7 相关内容。
- COTTI 专业渠道、管理员切换、Agent 数据迁移和部署白名单仍为二开能力。

## 历史数据升级

脚本默认只检查，不修改数据库：

```bash
DATABASE_URL=... bun run db:migrate:cotti-gemini-37
```

确认输出后显式执行：

```bash
DATABASE_URL=... bun run db:migrate:cotti-gemini-37 -- --apply
```

脚本会：

1. 将平台 Chat / Agent 模型池中显示名为 `COTTI-专业` 的 3.6 映射更新为 3.7；
2. 将 Agent 缺省模型从 3.6 更新为 3.7；
3. 分批把现有 Vertex AI Agent 的 3.6 模型更新为 3.7；
4. 保留历史消息、Topic、Tracing 和审计记录中的原始模型 ID。

脚本使用事务和 advisory lock，可重复执行；无待升级数据时为 no-op。

## 后台版本切换

平台管理中的切换操作使用单个数据库事务完成：

1. 同时替换 Chat 与 Agent 模型池中的 `COTTI-专业` 映射；
2. 当 Agent 缺省模型为专业渠道时，同步更新缺省模型；
3. 批量更新现有 Vertex AI 专业 Agent 的模型 ID；
4. 在 3.6 与 3.7 使用的 `thinkingLevel` / `thinkingLevel3` 字段之间转换，避免旧参数导致
   上游 `400 INVALID_ARGUMENT`；
5. 保留历史消息、Topic、Tracing 和审计记录中的原始模型 ID。

切换前界面会显示目标版本和受影响 Agent 数量，并要求管理员二次确认。目标模型未在服务端
部署时，服务端拒绝切换。

## 环境配置

部署环境必须在以下变量中同时保留 3.6 和 3.7；平台配置负责只向用户暴露当前选中的
`COTTI-专业` 映射：

- `VERTEXAI_MODEL_LIST`
- `NEXT_PUBLIC_MODEL_VISIBLE_ALLOW`
- `NEXT_PUBLIC_MODEL_DISPLAY_NAMES`

建议环境值分别使用底层名称 `Gemini 3.6 Flash`、`Gemini 3.7 Flash`，不要同时把两个候选
模型直接命名成 `COTTI-专业`。`SYSTEM_AGENT` 属于后台辅助任务，不随专业渠道切换。

内置搜索白名单当前使用 `vertexai/gemini-*`，无需单独增加 3.7。

## Docker 构建基线

2026-08-14 首次候选镜像构建时，`next` 的宽泛版本范围从已验证的 16.3.0 漂移到
16.3.1。该版本生成的 standalone 镜像遗漏 `@swc/helpers` ESM 文件，数据库迁移后在
Next.js 启动阶段报 `MODULE_NOT_FOUND`。候选容器门禁阻止了切换，原 chatdev 未受影响。

本分支将 `next` 精确锁定为当前已验证可运行的 `16.3.0`，避免同一提交因构建日期不同
产生不可运行镜像；未增加运行时兼容层。升级 Next.js 时必须重新执行候选端口启动门禁。

## 回滚

保留升级前数据库备份和 `.env`。回滚顺序为：

1. 确认环境变量同时包含 3.6 和 3.7；
2. 在平台管理中将专业渠道切换回 3.6；
3. 验证模型列表、Agent 数量和真实文本调用后，再隐藏 3.7。
