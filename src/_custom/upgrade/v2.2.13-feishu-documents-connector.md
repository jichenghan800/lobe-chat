# COTTI 飞书资料连接器二开说明（v2.2.13）

## 目标

- 落地日期：2026-08-05。
- 用户可见名称统一为 “飞书资料”。
- 内部 identifier 保持 `feishu-documents`，读取工具保持不变，新增飞书官方 MCP `create-doc` 用于把对话内容沉淀为新文档。
- 名称统一不能破坏已存在的个人 OAuth 授权、Agent `plugins` 配置、数据库关系和历史工具调用。

## 为什么此前中英文不一致

连接器详情页通过 `connectorPreset.feishuDocuments.title` 本地化为 “飞书资料”，但预设数据库名称和服务端生成的 ToolManifest 标题仍是 `Feishu Documents`。因此设置页显示中文，而提示词 action tag、模型工具清单和运行记录会继续显示英文。

这不是模型自动翻译导致的，而是两条名称来源没有统一。

## 最终命名规则

| 字段                          | 值                 | 是否允许修改           |
| ----------------------------- | ------------------ | ---------------------- |
| 用户可见名称 / 中文运行时标题 | `飞书资料`         | COTTI 固定             |
| 英文 locale 展示名            | `Feishu Documents` | 由 i18n 提供           |
| Connector identifier          | `feishu-documents` | 禁止修改               |
| Preset ID                     | `feishu_documents` | 禁止修改               |
| MCP 工具名                    | `search-doc` 等    | 飞书协议字段，禁止翻译 |

内部标识和工具函数名属于机器协议，不应该翻译。用户在中文界面看到的连接器标签、插入输入框的工具标签和服务端运行时连接器标题统一为 “飞书资料”。

## 新建文档能力（2026-08-05）

业务目标是把有价值的聊天记录新建为用户自己的飞书文档，不开放对既有文档的任意编辑、评论、消息写入或删除能力。

- 工具白名单新增 `create-doc`；继续禁止 `update-doc`、`add-comments`、消息和删除类工具。
- 使用每个 LobeHub 用户自己的 Feishu User Access Token，新文档以该授权用户身份创建；不改为租户机器人统一身份。
- `create-doc` 可以在 “我的文档库” 或用户指定的知识空间节点中创建文档，并写入本次生成的正文。
- 按飞书官方远程 MCP 要求新增 OAuth scopes：`docx:document:create`、`docx:document:write_only`、`wiki:node:read`、`wiki:node:create`、`docs:document.media:upload`、`board:whiteboard:node:create`；原有只读 scopes 保留。
- 飞书 scope 描述的能力范围大于单一工具，但 LobeHub 服务端仍以 `X-Lark-MCP-Allowed-Tools` 和同步 allowlist 双重限制，只向模型暴露 `create-doc` 这一项写操作。
- 已连接用户的旧 token 不含新增 scopes，升级后必须点击 “重新授权”；仅点击 “同步” 不能补充 OAuth 权限。
- 飞书开放平台后台必须先申请并发布上述权限，否则重新授权或调用 `create-doc` 会失败。
- 本次不开放 `update-doc`。超出 `create-doc` 单次内容上限的超长记录暂不自动续写，后续如确有需求，再单独评估受限追加能力与防误改机制。

## 旧授权与新工具同步保护（2026-08-06）

chatdev 真实会话 `tpc_qAkYX0cDJ4dj` 暴露了工具同步与 OAuth 授权版本不一致的问题：请求开始时连接器仍只有旧的读取工具；第一次 `search-doc` 调用触发后台同步后，数据库才出现 `create-doc`，但当前 Agent 运行不会中途重建 ToolManifest，模型因此回退调用系统 `createDocument`，并错误声称飞书 API 不支持创建文档。

同时，该用户数据库中的 `oidc_config.scopes` 仍为旧只读集合。后台同步只能刷新工具定义，不能给已经签发的 User Access Token 增加权限。

保护逻辑如下：

- 以 OAuth token 返回的 `credentials.scope` 为已授权事实来源；不能只看预设期望 scopes 或远端 MCP 工具列表。
- 只有 token 同时包含 `docx:document:create` 和 `docx:document:write_only` 时，才向远端 allowed-tools header、数据库同步、Agent ToolManifest 和最终工具执行暴露 `create-doc`。
- 旧数据库里即使残留 `create-doc` 工具行，运行时也会过滤，直接伪造调用同样由服务端拒绝。
- 服务端连接器列表只返回 `requiresReauthorization` 布尔值，不把 token 或 scope 明文发送到浏览器。
- 设置页显示持久的 “需要更新授权” 提醒和直接 “重新授权飞书” 动作；同步按钮不能替代 OAuth。

此改动不新增数据库字段和 migration。用户完成一次重新授权后，新 token 携带写入 scopes，提醒自动消失并开放 `create-doc`。

## 数据和升级影响

- 不新增表或字段，不需要 migration。
- 仅名称统一不要求重新授权；启用 `create-doc` 后，已授权用户需要重新 OAuth，以获取新增的文档创建 scopes。
- 用户下次重新连接时，现有数据库行会更新为规范中文名称。
- 不批量更新历史消息中的 `<tool label="Feishu Documents">`，避免无必要的数据改写；历史消息仍通过 `name="feishu-documents"` 正常识别。
- 下次升级先检查官方是否提供 connector displayName/localization hook；如果已有，保留稳定 identifier，删除本地运行时名称覆盖。

9. 重新授权后提醒消失；新会话明确要求存入飞书文档时调用 `create-doc`，返回 `feishu.cn` / `larksuite.com` 文档链接，而不是 `/agent/.../docs/...`。

## Chat 模式显式工具准入修复（2026-08-06）

重新授权后，chatdev 真实会话仍未调用 `create-doc`。消息的 action tag 已正确保存为 `feishu-documents`，数据库工具列表也包含 `create-doc`，但模型运行时只拿到了 Chat 模式默认的生图、知识库、记忆和联网工具。

根因是 Chat 模式的严格工具白名单没有区分 “Agent 预设 / 固定工具” 和 “用户本轮通过 `@` 明确选择的工具”，导致后者同样被过滤。修复保持原有轻量化边界：

- Chat 模式继续不自动加载 Agent 固定工具、always-on 工具或其他运行时工具。
- 仅将本轮 `selectedToolIds` 加入 Chat 模式白名单；未被用户本轮选择的固定工具仍不可用。
- 客户端直连运行和服务端 Gateway/Queue 运行使用相同规则，避免运行模式切换后行为漂移。
- 不增加数据库字段或 migration，不改变 Agent 模式的工具激活逻辑。

二开触点：

- `src/helpers/toolEngineering/index.ts`：客户端 Chat 模式只额外放行本轮显式选择的工具。
- `src/store/chat/slices/agentRun/actions/transports/client/streamingExecutor.ts`：将解析出的 `selectedToolIds` 独立传入工具引擎，不与 Agent 固定工具混为同一授权来源。
- `apps/server/src/modules/Mecha/AgentToolsEngine/{index,types}.ts`：服务端工具引擎镜像相同准入规则。
- `apps/server/src/services/aiAgent/index.ts`：服务端运行链路透传本轮显式工具选择。

回归要求：在 “对话” 模式下，`@飞书资料` 后可以调用 `create-doc`；同一 Agent 中其他未在本轮选择的固定工具不能因此被放开。

## 飞书聊天记录只读查询（2026-08-06）

飞书官方远程 MCP `https://mcp.feishu.cn/mcp` 当前只覆盖云文档场景，不能通过扩充远端 allowed-tools header 获得聊天记录。因此本项目继续复用同一个 “飞书资料” 连接器和每个用户自己的 User Access Token，在服务端增加受控的飞书 OpenAPI 虚拟工具，不部署第二套 stdio MCP，也不保存应用级租户 token。

新增工具：

| 工具                 | 能力                                            | 明确限制                                              |
| -------------------- | ----------------------------------------------- | ----------------------------------------------------- |
| `list-group-chats`   | 分页列出授权用户所在的群                        | 只列群，不枚举全部单聊                                |
| `list-chat-messages` | 按已知 `chat_id` / `thread_id` 分页读取历史消息 | 单聊和群聊都要求明确 ID；不做全租户、全会话关键词扫描 |
| `get-chat-message`   | 按已知 `message_id` 读取单条消息                | 不绕过飞书数据权限                                    |

权限与安全边界：

- OAuth 新增 `im:message:readonly`、`im:message.p2p_msg:get_as_user`、`im:message.group_msg:get_as_user`；已有 `im:chat:read` 保留。
- 工具只使用当前 LobeHub 用户自己授权的 User Access Token。不同用户的 connector 和加密 token 继续按现有用户 / 工作区作用域隔离。
- 三个消息工具初次同步默认均为 `needs_approval`，模型每次读取前必须由用户确认；用户之后可在连接器设置中自行调整。
- 服务端单次最多返回 50 条，默认 20 条，只返回飞书分页结果及 `page_token`，不自动翻页抓取全部历史。
- 不开放发消息、撤回、删除或应用身份的全租户读取；群成员接口仅用于把当前会话中的
  `open_id` 映射为已验证姓名，不作为独立工具暴露，也不抓取无关群组。
- 群列表接口只能发现群聊。单聊历史接口本身支持 p2p，但前提是已经获得该单聊的 `chat_id`；
  2026-08-08 起由后文的独立消息搜索工具补足单聊消息发现能力。
- 飞书侧仍会校验用户本人是否有权查看目标会话；群聊场景还受应用机器人是否在群内等平台规则约束。

实现触点：

- `src/const/connectorPresets.ts`：记录消息 scopes 和本地虚拟工具白名单；远端 `X-Lark-MCP-Allowed-Tools` 仍只包含官方文档 MCP 工具。
- `apps/server/src/services/connector/feishuMessages.ts`：参数校验、分页上限、User Access Token 调用和标准 MCP 结果转换。
- `apps/server/src/services/connector/sync.ts`：远端文档工具与本地消息工具合并同步；旧 token 不创建消息工具行。
- `apps/server/src/services/connector/exec.ts`：虚拟工具走飞书 OpenAPI，其余文档工具继续走官方远程 MCP。
- `apps/server/src/routers/lambda/connector.ts`：旧授权缺少消息 scopes 时显示重新授权提示。

不新增数据库表或 migration。飞书开放平台后台先申请并发布消息 scopes，用户再重新授权；仅同步工具不能给旧 token 增加权限。

## 飞书电子表格只读查询（2026-08-08）

飞书官方远程 MCP 的 `fetch-doc` 明确不支持电子表格和多维表格。Wiki 链接可以解析到节点，但当节点的 `obj_type` 为 `sheet` 时，官方工具仍会按 Docx 读取并返回 `not found`。本项目因此复用同一个 “飞书资料” 连接器和每个用户自己的 User Access Token，增加独立、可拆除的 Sheet OpenAPI 虚拟工具。

新增工具：

| 工具          | 能力                                              | 明确限制                                                                     |
| ------------- | ------------------------------------------------- | ---------------------------------------------------------------------------- |
| `fetch-sheet` | 解析 Wiki/Sheets 链接，列出工作表并分段读取单元格 | 只读；默认 100 行 × 30 列，单次最多 5,000 个单元格；长单元格和总响应均有上限 |

权限与安全边界：

- OAuth 新增最小只读 scope：`sheets:spreadsheet:readonly`，不申请任何 Sheet 写入权限。
- 工具只使用当前 LobeHub 用户授权的 User Access Token；飞书仍校验该用户本人是否有权查看目标电子表格。
- Wiki URL 先通过节点 API 获取 `obj_type` 和 `obj_token`；仅 `obj_type=sheet` 进入 Sheet 读取，其他类型提示使用对应文档工具。
- 读取接口返回工作表列表、当前分页范围、单元格值和 `next_start_row`；模型需要显式翻页，不会自动抓取整份大表。
- 单次限制为 200 行、50 列且总计不超过 5,000 个单元格；单个超长单元格和总工具结果会截断并返回标记，避免电子表格内容撑爆模型上下文。
- `fetch-doc` 的同步描述追加 “电子表格请使用 `fetch-sheet`”，避免模型重复调用官方不支持的路径。

独立实现与最小接入点：

- `apps/server/src/services/connector/feishuSheets.ts`：链接解析、类型分发、OpenAPI 请求、分页和输出限制，主体逻辑独立存在。
- `src/const/connectorPresets.ts`：注册只读 scope、虚拟工具和授权判断。
- `apps/server/src/services/connector/sync.ts`：将已授权的 `fetch-sheet` 合并到工具列表，不把名称发送给官方文档 MCP。
- `apps/server/src/services/connector/exec.ts`：仅为 `fetch-sheet` 增加本地执行分支，其他官方 MCP 工具保持原路径。

不新增数据库表或 migration。飞书开放平台后台必须先申请并发布 `sheets:spreadsheet:readonly`，用户再重新授权；同步工具不能给旧 token 增加权限。若未来官方 MCP 原生支持 Sheet，可删除独立服务和上述注册点，恢复为官方工具。

## 飞书消息搜索（2026-08-08）

- 新增独立的 `search-chat-messages` 本地只读工具，调用飞书官方
  `POST /open-apis/search/v2/message`，使用每位用户自己的 `user_access_token`。
- 新增 `search:message` OAuth scope；消息搜索仍同时要求既有的单聊、群聊消息读取权限，
  不使用应用身份扩大数据范围。
- 支持用 `chat_type=p2p_chat` 查询当前用户可见的单聊消息，支持关键词、发送人、会话、
  消息类型和 Unix 秒级时间范围过滤；单页最多 10 条，搜索返回的消息 ID 会在服务端以
  同一用户身份读取详情。
- `list-group-chats` 默认按最近活跃时间倒序，并明确返回能力边界：该工具只列群聊；发现
  单聊消息必须使用 `search-chat-messages`，不能据此推断飞书不支持单聊查询。
- 保持二开隔离：远端飞书文档 MCP 的工具白名单不变，新能力继续通过 COTTI 服务端虚拟
  工具接入，便于后续官方升级时单独迁移。

## 飞书消息身份与时间确定性（2026-08-08）

chatdev 话题 `tpc_pEU542qfIiMP` 暴露了两个不能交给模型推断的字段：飞书消息历史接口只返回
发送者 `open_id`，模型把消息正文与 @ 提及中的姓名误当成发送者姓名；同时模型自行换算
毫秒时间戳，将 09:33 错写为 10:53，整段产生约 80 分钟偏移。

- OAuth 预设新增最小只读权限 `im:chat.members:read`，仅用于获取当前用户所在群的成员 ID 与
  姓名。缺少该权限时仍可读取消息，但返回 `sender.id`、`name_verified=false` 和明确警告，
  禁止根据提及或正文猜姓名。
- `list-chat-messages` 和 `get-chat-message` 由服务端返回 `create_time_local`、
  `update_time_local` 与明确 `time_zone`，固定为 `Asia/Shanghai`；工具说明要求模型直接使用，
  不再自行换算毫秒值。
- 用户要求 “今天” 或其他日期时只传 `date=YYYY-MM-DD`，由服务端固定按 `Asia/Shanghai`
  生成 00:00:00 到次日 00:00:00 前一秒的 Unix 范围，模型不再选择时区或自行计算时间戳。
  未传时间范围时结果明确返回 `range_filter_applied=false` 和警告，不能把普通分页结果描述成
  当日记录。
- 会话消息单页上限从 50 收紧为 20；正文解析为短文本并限制为 1,000 字符，避免富文本卡片
  把工具结果截断成无效 JSON。需要更多记录时通过 `page_token` 继续分页。
- 姓名解析按 chat\_id 去重，单次最多查询 5 个会话、每个会话最多 5 页群成员；任何成员接口
  失败都降级为未验证 ID，不影响消息读取本身。

## 飞书消息纯文本报表原料（2026-08-08）

chatdev 话题 `tpc_vrmQI3icL8e2` 进一步暴露了三处问题：模型把 “今天” 错误换算为当天 08:00
开始；20 条搜索详情生成约 25KB 工具结果，运行时归档截断后成为无效 JSON；飞书 `post`
消息同时返回 `content` / `content_v2`，旧递归解析重复正文，最终回答只展示模糊的 “图文 / 富
文本消息” 说明，无法直接作为统计和报表原料。

- 搜索默认及最大页长统一收紧为 10 条，单条正文最多 1,000 字符，确保常规工具结果保持在
  Agent 运行时 25KB 归档阈值以下；继续通过 `page_token` 查询后续结果，不截断 JSON 字符串。
- `search-chat-messages` 和 `list-chat-messages` 新增 `date` 参数，服务端按固定中国时区计算整天
  范围；`date` 与手工 `start_time` / `end_time` 互斥，消除模型日期换算偏差。
- 读取消息详情时传 `card_msg_content_type=user_card_content`，用途只是取得原始消息载荷并在
  服务端转为纯文本；不会把飞书富文本卡片直接交给用户。解析优先使用 `content_v2`，不重复
  遍历 `content`，并保留 @ 用户、正文链接及文件名。
- 每条消息明确返回 `create_time_local`、经过验证的 `sender` 和 `text_for_analysis`。后者把
  正文、链接以及 `[图片]` / `[文件: 文件名]` 标记合并为可直接汇总的纯文本；搜索结果扁平化
  为 `items`，不再要求模型解读多层详情包装。
- 不返回卡片跳转，不增加图片读取或图片生成链路。图片只有资源标记时必须如实写为 `[图片]`，
  禁止模型根据上下文编造图片内容，更不能调用生图工具替代读取。
- 上述能力继续使用当前用户自己的 User Access Token 和既有消息读取 scopes；不新增权限、
  数据库字段或 migration，也不修改官方远程文档 MCP。
- `query` 只匹配消息正文，不能用于证明单聊对象身份。查询 “与某人沟通记录” 时必须先从飞书
  返回的发送者或 @ 提及中取得已验证 `open_id`，再用既有 `from_ids` 定位单聊；若无法验证，
  必须停止，不能清空关键词后把任意单聊当成目标联系人。
- 第一版曾要求模型组合 `search-chat-messages`、`list-chat-messages` 等通用工具完成身份发现。
  chatdev 真实测试中，轻量模型连续零工具调用并直接要求用户提供 `open_id`，说明多步规划本身
  不可靠，不能继续靠叠加提示词修补。
- 现新增单一高层只读工具 `query-chat-history`：输入精确人员名或群名及日期，服务端内部复用

  返回的精确 @ 提及或已验证发送者身份；群查询只接受群名完全匹配。找不到或存在同名时才返回
  一句自然语言澄清，不要求用户理解 `open_id`、`chat_id` 等技术字段。

  联系人接口、数据库表、migration 或权限，也没有在错误的模型规划外再包一层客户端逻辑。
- `query-chat-history` 默认权限为 `auto`，但只有用户在输入框明确选择 “飞书资料” 或把连接器固定

## 飞书整日聊天记录确定性分页（2026-08-19）

chatdev 话题 `tpc_KhVDoq2HzVTc` 两次执行 “读取我昨天的聊天信息，生成日报” 时，模型都调用了
`search-chat-messages` 的单页查询：第一次返回 10 条且 `has_more=true`，第二次又把范围缩成
`chat_type=p2p_chat`，同样返回 10 条且 `has_more=true`。两个模型都忽略了下一页 token，却把单页
结果表述为完整日报。该问题不是飞书权限、时区或模型内容理解问题，而是把确定性分页交给模型规划。

- 复用并扩展既有高层工具 `query-chat-history`，不新增第二套消息服务。`target_type=all`（默认）用于
  按北京时区读取某天当前用户可见的单聊和群聊；指定 `person` / `group` 时继续使用原有精确身份匹配。
- 高层工具由服务端自动消费飞书 `page_token`，跨页去重并返回紧凑的时间、已验证姓名和纯文本记录；
  低层 `search-chat-messages` / `list-chat-messages` 的显式单页语义保持不变。
- 结果新增 `complete`、`pages_read`、`message_count`、`failed_message_count` 和
  `continuation_page_token`。只有到达末页且没有消息详情读取失败时才返回 `complete=true`；模型不得把
  `complete=false` 的结果称为完整日报。
- 为避免再次触发 25,000 字符工具结果归档，紧凑记录达到安全边界时停止当前批次，并返回可续查 token；
  不提高低层工具页长，也不把截断后的无效 JSON 交给模型。
- 回归测试覆盖：全部聊天跨搜索页、命名群聊跨消息页、详情读取失败不得标记完整，以及大结果必须返回
  明确续查信息。
