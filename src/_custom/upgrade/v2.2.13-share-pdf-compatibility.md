# COTTI 分享 PDF 浏览器兼容修复（v2.2.13）

## 问题与结论

2026-08-21 在 chatdev 复现 “查询结果分享 → 生成 PDF” 不可用。服务端
`exporter.exportPdf` 连续返回 HTTP 200，响应体包含完整 PDF；PDF worker 也返回 HTTP
200。使用同一套 PDFKit 与字体在本机生成后，PDF.js 可以正常解析，因此故障边界位于浏览器
预览和下载阶段。

同步官方 `upstream-lobehub/canary` 到 `097c0a2e298167a60d13c39d6d95fe555f58db31`
后逐文件对照：`exporter.ts`、`usePdfGeneration.ts`、`PdfPreview.tsx` 与
`src/libs/pdfjs/index.tsx` 均与官方一致。原二开仅把下载后的 base-ui `toast` 换成 antd
`message`，不参与 PDF 生成或预览，因此不是本问题根因。

## 二开内容

1. 将服务端 base64 PDF 解码成 `Uint8Array` 后直接交给 React-PDF/PDF.js，不再使用
   `data:application/pdf;base64,...` URL。
2. 预览加载失败时显示明确失败状态，但保留已经生成的 PDF 和 “下载 PDF / 重新生成” 操作，
   避免预览故障阻断导出结果。
3. 下载复用同一份二进制转换逻辑，并延迟释放 Object URL，避免部分浏览器尚未开始读取就
   撤销 URL。
4. PDF 生成接口、权限、数据库和文件存储均不改变。

## Agent 长回复正文兼容（2026-08-21 补充）

### 现象与根因

Topic `tpc_pNK5THVhdGHC` 的最终回答在数据库中仍有约 7,406 个字符，但下载的 PDF
只有两个相同标题。只读诊断确认这是两个官方源码问题叠加：

1. Agent 工具链会由 `@lobechat/conversation-flow` 聚合成 `assistantGroup`。外层虚拟消息
   的 `content` 为空，真正的最终回答位于 `children`；官方分享模板却只读取
   `message.content`。
2. PDF 服务端会单独渲染 `title`，客户端生成的 Markdown 又以 `# title` 开头，导致标题
   重复。

对照 `upstream-lobehub/canary` 后确认正文选择、Markdown 模板和 PDF 服务端逻辑均与官方
一致；原 COTTI 差异仅为下载提示组件，不参与正文组装，因此本问题不是既有二开引入。

### 最小兼容改造

1. 分享文本与 PDF 复用官方已有的 `resolveAssistantGroupFinalContent()`，从
   `assistantGroup` / `supervisor` 的语义分段中取得最终作者回答，不自行解析 Agent 工具链。
2. PDF 调用生成 Markdown 时设置 `withTitle: false`，标题只交给服务端 PDF 渲染器输出一次；
   普通 Markdown 下载仍保留标题。
3. 单条消息分享和整个 Topic 分享共用同一正文解析规则，避免两条导出路径再次分叉。
4. 增加 “空 assistantGroup 外壳 + children 长正文” 和 “PDF Markdown 不重复标题” 的回归测试。

## 验收

1. 中文长对话可以生成并预览 PDF。
2. 浏览器无法预览时，页面明确提示，但 “下载 PDF” 仍可用。
3. 下载文件以 `%PDF-` 开头且可由 PDF 阅读器打开。
4. 重新生成后预览状态可以恢复。
5. `assistantGroup.content` 为空但 `children` 有最终回答时，PDF 和文本导出均包含完整正文。
6. PDF 标题只出现一次，普通 Markdown 文本导出仍保留一级标题。
